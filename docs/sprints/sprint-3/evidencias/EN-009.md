## Resumen

Una vez que RN-001 se cumple (`mAP@0.5 ≥ 0.85` en test set), exportamos `custom-v1.pt` a formato **ONNX** para que el backend FastAPI lo consuma vía `onnxruntime` (más rápido que cargar PyTorch en producción y sin dependencia de ultralytics en runtime).

El modelo ONNX se ubica en `ml/models/custom-v1.onnx`. El backend (Sprint 4, EN-011) lo carga desde ese path.

## Comando de export

```powershell
cd c:\Users\Patrick Isla\Desktop\notion\BackMangoVision

yolo export `
    model=ml/models/custom-v1.pt `
    format=onnx `
    imgsz=640 `
    opset=12 `
    dynamic=False `
    simplify=True
```

Outputs:
- `ml/models/custom-v1.onnx` — modelo en formato ONNX.
- `ml/models/custom-v1.pt` — PyTorch original conservado (backup).

## Smoke test post-export

```powershell
python -c "
import onnxruntime as ort
import numpy as np

session = ort.InferenceSession('ml/models/custom-v1.onnx')
input_name = session.get_inputs()[0].name
input_shape = session.get_inputs()[0].shape
print(f'Input: {input_name} shape={input_shape}')

# Dummy input para validar que el grafo no esta roto
dummy = np.random.randn(1, 3, 640, 640).astype(np.float32)
outputs = session.run(None, {input_name: dummy})
print(f'Outputs: {[o.shape for o in outputs]}')
print('OK ONNX inferencia funcional')
"
```

## Decisión: ONNX vs TorchScript vs raw PyTorch

| Formato | Pros | Cons | Decisión |
|---|---|---|---|
| **ONNX** | Sin dependencia PyTorch en runtime. Optimizable con onnxruntime-gpu. Estándar de industria. | Requiere conversión cuidadosa de operaciones no estándar. | ✅ Elegido |
| TorchScript | Mantiene 100% compatibilidad con PyTorch. | Requiere instalar torch en backend (pesado). | Descartado |
| PyTorch raw | Sin conversión. | Frágil: la inferencia depende de la versión exacta de ultralytics. | Descartado |

## Carpeta destino y convención de versionado

```
ml/models/
├── baseline-v0.pt              ← EN-005
├── custom-v1.pt                ← EN-006 (PyTorch backup)
├── custom-v1.onnx              ← EN-009 (consumido por backend)
└── custom-v2.onnx              ← si hay iteraciones futuras
```

El backend lee siempre `custom-vN.onnx` con la versión activa marcada en la tabla `ml_models` (HU-019 del Sprint 5).

## Notas técnicas

- **`imgsz=640`** debe coincidir con el `imgsz` usado en training. Si el backend recibe una imagen de otro tamaño, le hace resize a 640×640 antes de inferir.
- **`opset=12`** es compatible con onnxruntime ≥ 1.10. Si en el futuro queremos correr con TensorRT o providers GPU específicos, podemos subir el opset.
- **`dynamic=False`**: input shape fijo. Más rápido pero pierde flexibilidad. Si necesitáramos procesar batches variables, usar `dynamic=True`.
- **`simplify=True`** corre `onnx-simplifier` para optimizar el grafo. Reduce tamaño del archivo y mejora la latencia.
