## Resumen

JWT es stateless: el logout efectivo se hace borrando el token del cliente. El backend expone `POST /api/auth/logout` (204 No Content) como punto explícito para el frontend y para dejar preparada una blacklist/refresh-token en el futuro. La protección de rutas se hace vía dependencia `get_current_user` que valida el JWT y la actividad del usuario.

## Archivos clave

- [backend/app/api/routes/auth.py](../../../../backend/app/api/routes/auth.py) — endpoints `POST /logout` y `GET /me`.
- [backend/app/api/deps.py](../../../../backend/app/api/deps.py) — `get_current_user` (401 si el token es inválido, expirado, o el usuario está desactivado).

## Cómo probar (manual)

```powershell
# Tras hacer login (ver HU-004) y guardar el token:
$TOKEN = "eyJhbGciOi..."  # el access_token de la respuesta

# Ver el usuario actual:
curl http://localhost:8000/api/auth/me -H "Authorization: Bearer $TOKEN"

# Logout:
curl -X POST http://localhost:8000/api/auth/logout -H "Authorization: Bearer $TOKEN"
# Respuesta: 204 No Content

# Acceder a /me sin token:
curl http://localhost:8000/api/auth/me  # → 401
```

## Notas técnicas

- El criterio "el JWT se elimina del almacenamiento del navegador" pertenece al frontend (HU-005-FE pendiente). El backend solo provee el endpoint y la dependencia.
- El criterio "redirige a `/login`" se implementará en el frontend con un `ProtectedRoute` que envuelva las rutas privadas y haga `Navigate to="/login"` si no hay token en `localStorage` o si `GET /me` responde 401.
- En Sprint 4/5, si se implementa una blacklist de tokens (para casos de "logout forzado por admin"), este endpoint pasaría de no-op a registrar el `jti` del token en una tabla con expiración igual a la del JWT.
