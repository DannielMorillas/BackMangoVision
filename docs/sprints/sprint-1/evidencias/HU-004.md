## Resumen

`POST /api/auth/login` autentica con email + password, verifica `bcrypt`, comprueba `is_active`, emite un JWT HS256 de 8 horas y actualiza `last_login_at`.

## Archivos clave

- [backend/app/core/security.py](../../../../backend/app/core/security.py) — `hash_password`, `verify_password`, `create_access_token`.
- [backend/app/api/routes/auth.py](../../../../backend/app/api/routes/auth.py) — endpoint `POST /api/auth/login`.

## Tests automatizados (6 verdes)

| Test | Verifica |
|---|---|
| `test_login_ok_returns_jwt_and_user` | Login válido → 200 con JWT decodificable + datos del usuario |
| `test_login_email_is_case_insensitive` | `ADA@example.com` ≡ `ada@example.com` |
| `test_login_wrong_password_returns_401` | Contraseña incorrecta → 401 con mensaje genérico |
| `test_login_unknown_user_returns_401_same_message` | Email inexistente → 401 **con el mismo mensaje** (evita filtrar usuarios) |
| `test_login_inactive_user_returns_403` | Usuario `is_active=false` → 403 |
| `test_login_updates_last_login_at` | Tras login, `last_login_at` queda registrado |

## Criterios verificados

- [x] El formulario valida que ambos campos estén completos (Pydantic `EmailStr` + `min_length=1`).
- [x] Si las credenciales son correctas, devuelve JWT — el frontend redirige al dashboard.
- [x] Si son incorrectas, mensaje claro de error.
- [x] El backend retorna un JWT válido por **8 horas** (`JWT_EXPIRES_HOURS=8`).
- [x] La contraseña se compara con hash **bcrypt** en la BD (no plain text).

## Notas técnicas

- Usamos `bcrypt` directamente (no `passlib`) para evitar el bug conocido de `passlib==1.7.4` con `bcrypt 4.x` en Python 3.12.
- El JWT incluye `sub` (user_id), `role`, `iat`, `exp`, `type: "access"`. El campo `type` deja la puerta abierta para distinguir access vs refresh tokens en sprints siguientes.
- El mensaje "Credenciales inválidas" es idéntico para usuario desconocido y contraseña errónea — **no se filtra qué emails están registrados**.
